## 一、项目是什么

把蓝牙心率（标准 BLE 心率广播，GATT `0x180D` / `0x2A37`）实时叠到 OBS 画面上。
一条红色心率线横穿画面 + 一个像素角色 + 大号心率数字。

**核心设计原则：颜色通道与特效通道完全独立**

- **颜色如实反映强度**（不伪造心率）：强度 → 白 / 黄 / 橙 / 红
- **特效只管节目效果**：独立的"爆发"脉冲（残影、水花、红温、脉冲光）

## 三、算法（当前实现，冻结版）

```
B   = 个人基准，开播头 3 分钟锁定后不再漂移（或控制台手动校准）
P90 = 最近 10 分钟第 90 百分位心率
R   = clamp(P90 − p90Offset,  B + minGap,  B + maxGap)    ← 满红阈值，15 秒时间常数缓慢跟随
强度 = clamp((bpm − B) / (R − B), 0, 1)
颜色：白 = B    黄 = B + (R−B)×0.4    橙 = B + (R−B)×0.7    红 = R
强度走 Attack(2s) / Release(6s) 双时间常数
特效：burstWindow 内上涨 ≥ burstRise 且当前 ≥ B + burstAbove
      → 触发约 1 秒爆发（burst = 1，按 dt×1.1 衰减），冷却 burstCooldown 秒
满红迟滞：连续达阈值 redHold 秒才算满红；回落 redDrop bpm 才解除
离线：超过 offlineAfter 秒没新数据 → 显示 --- + 红点
```

**当前参数**（`params.json` / `DEFAULT_PARAMS`）：

| 参数 | 值 | 参数 | 值 |
|---|---|---|---|
| `minGap` | 22 | `redHold` | 2 |
| `maxGap` | 30 | `redDrop` | 5 |
| `p90Offset` | 3 | `offlineAfter` | 5 |
| `anchorTau` | 15 | `burstRise` | 10 |
| `attack` / `release` | 2 / 6 | `burstAbove` | 15 |
| `yellowAt` / `orangeAt` | 0.4 / 0.7 | `burstWindow` | 30 |
| `skin` | `xianyu` | `burstCooldown` | 30 |

另有两个**服务端**阈值（不是上面那套）：`warn = 120`、`danger = 150`。

# 需求 1：参数是否合理？

## 我的疑点（供你参考，不要被带偏，请独立判断）

1. **满红门槛可能高于真实峰值**：若平静时 B≈72，则 R = B+22 ~ B+30 = **94~102**，而全部 27586 个样本里 **P99 只有 92、最高 104**。也就是说除了极少数峰值，**几乎红不了**。
2. **`warn=120` / `danger=150` 永远达不到**（历史最高 104）→ `zone` 永远是 `rest`。而前端用 `zone` 驱动角色状态帧（例如 `xianyu` 皮肤的 `attack` 帧判据里有 `zone === 'danger'`），这条分支**永不触发**。
3. **`burstRise=10` + `burstAbove=15` 偏严**：需要"30 秒内涨 ≥10bpm"**且**"当前 ≥ B+15"（B≈72 时即 ≥87bpm）。而 P90 才 81、P99 才 92 → 实测很少能满足。
4. **基准 B 的稳定性存疑**：各场次 P50 从 **65 到 82** 波动（见上表）。"开播头 3 分钟锁定 B" 意味着同一套参数在不同场次会得到完全不同的阈值。

## 请回答

1. 按这组数据，`minGap=22 / maxGap=30` 合理吗？给出建议值**和推导过程**。
2. `warn`/`danger` 应该下调到多少？（注意它们同时被前端用作皮肤状态切换依据）
3. `burstRise` / `burstAbove` 是否过严？给出建议值。
4. "开播头 3 分钟锁定基准"这个机制要不要改？怎么改更稳？
5. **如果只能改 3 个参数**，你改哪 3 个、改成多少、依据是什么？

# 需求 2：把桌面前端控制台"集合进代码里"

## 现状

| 文件 | 形态 | 问题 |
|---|---|---|
| `heartrate_gui.py` | **独立 tkinter 窗口**（305 行） | 和网页控制台 `/console` **功能重叠**，但两套实现各写各的：皮肤下拉、参数滑杆、启停服务、校准基准都是两份代码 |
| `web/console.html` | 网页控制台（408 行） | 同样功能 |
| `heartrate_hud.py` | 桌面悬浮窗（852 行） | 又是第三份皮肤/参数逻辑 |

三处都在重复实现"皮肤选择 + 参数显示 + 心率显示"，**改一个参数要同步改三个地方**，已经出现过不一致（例如桌面前端用的是自己硬编码的参数默认值，不是服务端的）。

## 想达到的目标

**让桌面控制台不再是一份孤立代码，而是"项目的一部分"**，具体我希望你判断并给出方案：

1. **要不要统一到一个前端？** 例如：
   - 方案 A：桌面控制台改为**套壳网页**（tkinter 里嵌 WebView / 或直接打开浏览器），彻底消除重复实现；
   - 方案 B：保留原生 tkinter，但**参数与皮肤全部走服务端 API**（`/params`、`/hr`、`/calibrate`），不再本地硬编码；
   - 方案 C：保持现状，只做"三处共享一份配置常量"的最小改动。
   
   请结合这个项目的实际（单机、OBS、tkinter 无额外依赖、Windows）给出推荐，并说明代价。

2. **新增一个"参数总览"能力**：现在参数分散在 `params.json` + 各前端硬编码里。请设计一个**单一数据源**（服务端 `/params`），让所有前端只读它。

3. **请判断是否值得把 `params.json` 里的参数按用途分组**（例如 `color.*` / `effect.*` / `device.*`），还是保持平铺。注意不要破坏现有的 URL 参数覆盖机制（`?minGap=22&...` 优先级最高）。

## 约束（重要，不要违反）

- **不要改心率算法本身**（P90 / attack-release / burst 判据 / 满红迟滞），除非需求 1 明确要求调参数值
- **不要引入图片资源**（`xianyu` 皮肤已破例，其余保持"纯 Canvas 代码绘制"）
- **保持零/极少依赖**：服务端只有 `bleak` + `aiohttp`；桌面前端只用标准库 tkinter
- **OBS 里现成的浏览器源不要动**（URL `http://127.0.0.1:8080/?skin=xianyu`，尺寸 520×170，位置左上角）
- 个人数据（`logs/`、`params.json`、`devices.json`）不进 git 仓库
