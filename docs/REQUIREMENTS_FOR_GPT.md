# 需求 B：统一前端（"各忙各的"问题）

## B.1 我实测的根因

| 界面 | 取数方式 | 周期 | 问题 |
|---|---|---|---|
| 桌面 GUI（`heartrate_gui.py`，tkinter） | 轮询 `/hr` | **5 秒** | 最慢 |
| 桌面悬浮窗（`heartrate_hud.py`，tkinter） | 独立线程 `_poll_loop` | 0.5 秒 | 另持一份**本地参数副本** |
| OBS 叠层（`web/pixel.html`） | `EventSource /events` | 实时 | 正常 |
| `/console` 工作台 | 自己的 `fetch('/hr')` | 各自周期 | — |

**服务端有 `/events`（SSE 推送心率快照），但没有"配置变更广播"**。

**表现**：在 `/console` 改皮肤/参数后——
- 悬浮窗要等它自己的检测周期（约 2 秒）再自己判断一次
- GUI 控制台**最多 5 秒**才反映
- 桌面悬浮窗还持有一份本地参数副本（`load_remote_params`），只在特定条件下重载

→ 用户感受就是「控制台、悬浮窗、OBS 网页各忙各的」。

## B.2 建议的最小可行改法（请判断）

1. 服务端维护 `params_version`，`/events` 的快照里带上它；
2. **所有前端统一从同一通道取数**（tkinter 两个也可以连 SSE，或至少把轮询周期统一到 1 秒且共用同一解析逻辑）；
3. **桌面悬浮窗去掉本地参数副本**，皮肤/参数一律以服务端为准；
4. `/console` 保存后**主动广播**（`/events` 立即推一条带新 `params_version` 的快照），使所有前端同帧同步。

## B.3 请明确回答

- SSE 是选对了的通道吗？还是应该改成 WebSocket（需要双向）？
- tkinter 端接 SSE 值不值得（要引入线程 + 事件循环适配），还是"统一 1 秒轮询 + 同一解析函数"更务实？

# 需求 C：分档迟滞 + 档位边界用绝对值

## C.1 实测证据（这是必须加迟滞的理由）

部署方实测：`material-integrated` 那套 **6 档每档只有 3.5~4 bpm 宽**。
按 `R−B = 22` 换算：

```
idle        72.0 ~  76.0 bpm   宽 4.0
alert_low   76.0 ~  79.5 bpm   宽 3.5
alert_mid   79.5 ~  83.4 bpm   宽 4.0
tense       83.4 ~  87.0 bpm   宽 3.5
high        87.0 ~  90.5 bpm   宽 3.5
charge      90.5 ~  94.0 bpm   宽 3.5
```

而**心率读数天然抖 ±1~2 bpm**（`logs/` 里相邻样本经常跳 1~3）→ **临界处必然反复换图**。

更糟的是实测有一次 `R−B` 只有 **12.7 bpm**（`B=93, R=105.7`，因为 `P90` 在动），那档宽只剩 2 bpm。

## C.2 我建议的两个改法

1. **必须加迟滞**（`studio-gradient` 已有，逐级 0.035，方向正确，建议保留并可能加大）
2. **档位边界改用绝对 bpm 差**：例如按 `bpm − B` 的 `0 / 4 / 8 / 12 / 16` 分档，
   而不是按归一化强度 `(bpm−B)/(R−B)` 分档。
   **理由**：归一化分档的档宽 = `(R−B) × 档比例`，而 `R−B` 随 `P90` 浮动（实测 12.7~30），
   导致**同一套参数在不同时刻档宽差一倍以上**。用绝对 bpm 差则与 `R−B` 解耦。

## C.3 请明确回答

- 保 5 档还是 6 档？档位分界用什么值？（结合 §0.4 的真实数据：P50 72 / P90 81 / P99 92 / 最高 104）
- 迟滞用多大？（0.035 是否足够，还是要按 bpm 设绝对迟滞如 ±2 bpm）
- 事件帧（`burst` / `recover` / `thrust`）的阈值是否也要调？（现在 `burst>0.42 → burst`、`>0.08 → recover`）

# 需求 D：基准 B 的锁定机制不可靠（有实测证据）

## D.1 现象

**实测：基准被锁到了 93，而用户真实平静心率约 72**（历史 P50）。
结果：心率 **82** 时 `flush = 0`（连"待机"档都到不了），画面永远是灰白待机。

原因：`base_heart()` 在"样本数 ≥ 40"时就会用
`max(45, min + (avg − min) × 0.25)` 估算基准。
**如果用户点「校准基准」时刚好不平静（或在"开播头 3 分钟"内处于活动状态），基准就被永久锁高。**

## D.2 请回答

- 现在的"开播头 3 分钟锁定"是否太激进？是否可以改成**持续慢跟随**（例如 10 分钟窗口的 P25，时间常数 60 秒）？
- 是否要在 UI 上**显式提示"基准偏高/偏低"**（例如显示 `B` 与最近 10 分钟 P25 的差，超过 8 bpm 就警告）？
- 手动「校准基准」是否应该要求**连续 60 秒都在 P25 附近**才允许锁定，而不是取最近 60 秒的平均？

# 需求 G：v3 突刺特效遗留问题（`ISSUES_FOR_REVIEW.md` 第 1~8 条）

摘要（详细证据见该文档）：

1. **`dash` 包络用反**：`sin((1−burst)·π)` 在 `burst=0.5` 时位移最大、`burst=1` 时**归零** → 最激烈的一刻鱼不动，且会"冲出去再退回来"。建议 `sin(burst·π)`。
2. **水花被心率线淹没**：水花 y 落在 `centerY ± 6~11px`，**正好在心率 zigzag 上**。
   ⚠️ 改 z-order **无效**（已实测），必须换位置。可用空白带：上 `y≈30~60`、下 `y≈100~165`。
3. **残影可用空间不足**：鱼锚在 `fishX=12`，左缘只有 12px，三条残影中两条完全在画布外。
4. **520×170 中线拥挤（根问题）**：鱼、数字、心率线全压在水平中线上，任何画在中线的特效都会被淹。可选：加宽画布到 640 / 垂直分层 / 特效移到上方空白带。
5. 两个作用域各有一个 `dash`（其中一个死变量）；`pixel.html` 顶部注释仍是旧描述。
